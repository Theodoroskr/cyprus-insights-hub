# ingest-compliance

- ComplianceHub monitoring: `compliance_sources` registry → hourly `ingest-compliance` (each source collected only when its `check_interval_hours` is due; parsers in `_shared/compliance.ts`, drafts in `_shared/complianceAi.ts`) → `compliance_items` in `review`; one record can sit in several `sections`, dedupe is authority + official ID then canonical URL, content-hash changes on published rows wait in `pending_source_values` for an editor, and only `published` rows / `published` `fatf_releases` are public (RLS). Why: every public claim is editor-verified and tied to an official document.
- Sources with `compliance_sources.auto_publish` publish their drafted review records by themselves (`canAutoPublish` in `_shared/compliance.ts`: active source, never editor-reviewed, no pending source change, English title + summary), marked `auto_published`; public pages label them "not yet reviewed" and hide what-changed/action notes until an editor saves the record (which clears the flag). Why: fast coverage from trusted regulators without passing off unchecked interpretation as verified.
- Restrictive-measures acts come from the EU Publications Office Cellar SPARQL endpoint (`cellarRestrictiveQuery`/`parseCellarResults`) plus the EUR-Lex L-series RSS; EUR-Lex search pages are skipped (bot challenge). MOKAS reads its Lotus Notes notifications list (crawler fallback when the site is unreachable); the Cyprus Bar Association reads its WordPress API AML/sanctions categories, one record per circular number or headline+day (`cybarDedupeKey`). Seminars/events are skipped. Why: official machine-readable routes only, no duplicate records from re-posted notices.
- Editors can publish/reject several review records at once (`planBatchReview` in `src/lib/compliance.ts`: publish needs a section, title and summary, no pending source change, not a test row); batch-published rows count as editor-reviewed. Why: clear backlogs without bypassing the single-record publish checks.
